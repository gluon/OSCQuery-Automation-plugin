# Bench, 2026-11-08: Phase 3, slots, registry, send

What Phase 3 built was measured on the author's Windows machine (Windows 11, VS 2026, Debug
unless said otherwise), against the mock device on loopback and against the running WFS-DIY.
The REAPER rows are the devplan's done-when and are filled by hand at the DAW; the rest is the
test suite's own word (`tests/core/RegistryTests.cpp`, `lib/oscquery/tests/RawUdpSenderTests.cpp`),
repeatable with `ctest --preset vs-debug`.

## Against the mock device, loopback

| Check | How | Result |
| --- | --- | --- |
| One bundle per device per block, every instance in it | two instances, one slot each, 25 blocks 3 ms apart | **25 bundles holding 50 messages**: one per block, both messages in each |
| A multi-argument node is one message | an `fff` leaf on three consecutive slots, one argument moved | one message of three arguments, the two not automated carrying the tree's `VALUE`; all three moved in one block, still one message |
| Bundles split at the MTU | 32 messages, MTU set to 200 bytes | 4 bundles, none over 200 bytes, all 32 messages |
| CRITICAL on a UDP device | the fixture's CRITICAL toggle | one binary websocket frame holding the message; nothing on UDP |
| A TCP device | the mock with `OSC_TRANSPORT` TCP | one SLIP-framed bundle on one connection |
| Rate limiter, per bound path | 40 changes in 40 ms at 20 Hz | 2 messages, the last value arriving once its window opened |
| Time tags | the device marked as honouring them, offset -12.5 ms | the bundle's tag is NTP now minus 12.5 ms, within a millisecond; off again, the immediate tag |
| Unreachable device | a port nothing answers on, two instances | state `unreachable`, nothing sent, the unsent counted; pointed at the right address once, both instances send |
| The audio path allocates nothing | 500 blocks inside a counted region, ring mode and direct mode | **0 allocations**, both modes (the counting `operator new` proven to hear first) |
| Post to the wire | 200 blocks 2 ms apart, the mock timestamping each datagram as read | **median 96 µs, p99 227 µs, max 239 µs** from before `processBlock` to the receiver's read, gather deadline 500 µs included, Debug |
| The raw sender does not wait | 1,000 datagrams of 1,200 bytes back to back | 1,000 sent, 0 dropped, **3.5 ms** in all |
| The shared core library | the DLL this build makes, opened by the test executable | loads, ABI version 1, a registry of its own distinct from the executable's, sends to the mock through it |
| pluginval 1.0.4, strictness 5 | the Debug VST3 with 32 real parameters and the editor | SUCCESS, on this machine and in CI on three platforms |

The PRD's target is under a millisecond from the start of the block to the packet on the wire.
The number above is a stricter one (it includes the receiving thread's own wake) and is a tenth
of the target.

**On the Mac mini** (macOS 15.8.2, Apple silicon, Debug, `scripts/farm-check.sh` on a bundle clone,
the same day): all six CTest entries pass, the Release VST3 and AU build, pluginval 1.0.4 passes the
VST3 at strictness 5. The same cases there: 25 blocks from two instances as **25 bundles of two
messages**; post to the wire **median 209 µs, p99 337 µs, max 478 µs**; the rate limiter's forty
changes, which took 62 ms, as 2 messages. Two things the Mac taught before it passed: a device
thread that spins to its gather deadline overruns a macOS time-constraint budget and is demoted
until its wakes come milliseconds late (the gather now waits on the semaphore), and libc++'s
`counting_semaphore::try_acquire_for` polls with a growing back-off rather than waking on release,
so the wake is Apple's dispatch semaphore there (`src/core/registry/Wake.h`). Either alone merged
blocks a few milliseconds apart into one bundle.

**On the NUC** (Ubuntu 24.04, GCC 13, Debug, the same script, the same day): all six CTest entries
pass, the Release VST3 builds, pluginval 1.0.4 passes it at strictness 5 under Xvfb. The Linux link
of the plugin needed the core's and the library's object files inside JUCE's shared-code archive
(GNU ld scans an archive once); CI's Linux job is green with it.

## How the REAPER row is run

1. Rescan plugins in REAPER (Preferences, Plug-ins, VST, Re-scan). The plugin is "OSCQuery
   Automation 32" (Pix et Bel); `OSCQuery-Automation-Core.dll` sits beside the bundle in
   `%LOCALAPPDATA%\Programs\Common\VST3\`.
2. Insert it on a track, open its editor. The status bar's first line says whether the shared
   core library was found beside the plugin.
3. In the device list, type `127.0.0.1:5005` and Add; WFS-DIY appears once probed (DNS-SD finds
   nothing announced on the same Windows host, the Phase 2 finding). Click it: it joins the
   session and its tree loads below.
4. Click slot 1 in the table, then the input's `positionX` leaf in the tree (search `position`);
   the selection moves to slot 2; click `positionY`, then `positionZ`. The lanes rename on the
   next reopen of the FX window (REAPER renames the parameter, not a drawn lane: Phase 1).
5. Show the track's envelopes for the three parameters, draw curves, play. The source moves in
   WFS-DIY's map. The Test button sends the current value once without arming automation.
6. For the capture: duplicate the track to 32, play, and read Wireshark: one `#bundle` datagram
   per block to UDP 8000, with up to 96 messages in it (or two datagrams when over the MTU).
7. Save, close REAPER, reopen: the bindings are back, the lanes drive the same paths.
